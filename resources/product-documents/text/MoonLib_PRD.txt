MoonLib product requirements
OPC OS portfolio  |  30 September 2026  |  Version 1 for product review
MoonLib should remain a shared, policy-free library for MoonSuite package authors. The frozen baseline covers suite layout and path rules, conversation and pipeline wire contracts, experimental pack-support shapes, and low-level operating-system helpers. Four JavaScript pipeline-contract tests passed. This does not establish universal company, customer, task or artifact identity across MoonProj, MoonBook and MoonDesk. The recommended extension is a stable reference vocabulary proven by two real consumers, with versioned migration and replay; domain ownership and live service discovery must remain outside the library.
Repository maturity claim available library; release process maturing
This document defines the product baseline and a separately proposed roadmap. Acceptance tests below are release criteria unless a cited observation explicitly says they passed. Current source coverage does not establish production deployment or customer value.
Product philosophy and scope
Shared types are valuable when they let independently owned products exchange evidence without changing its identity or meaning. They are harmful when a convenient utility silently chooses company policy, discovers a service, infers approval or erases distinctions between a source, a task and an accepted artifact. MoonLib should offer deterministic building blocks whose effects and authority remain visible to the importing product.
The primary user is an integration developer rather than a founder operating a daily application. In the source-to-learning sequence, MoonLib provides reference and wire continuity. It cannot decide whether a source is credible, a commitment approved, a process authorized, an artifact inspected, a customer satisfied or cash received. Each domain owner must retain those decisions even when it uses a common record shape. A library dependency is not evidence that a complete business workflow interoperates.

User scenarios
Resolve suite layout and contained paths
MOONLIB-W01 | Baseline scope. A product needs its suite root or product home
1. Resolve the documented suite layout inputs
2. Construct the product-home or relative path using shared helpers
3. Validate the applicable containment rules
4. Return the deterministic result to the consumer
5. Let the consumer authorize any filesystem effect
Edge case A path contains traversal, platform-specific syntax or an ambiguous root; the helper must follow the documented target semantics.
Failure and recovery Invalid or escaping input returns a validation failure rather than guessing a usable path or granting access.
Acceptance Run supported layout fixtures on each declared target, including a traversal boundary and missing root; confirm a returned path alone performs no authorized write.

Exchange conversation journal and control records

Use operating system primitives explicitly
MOONLIB-W04 | Baseline scope. An importing product needs a filesystem process clock random or UUID helper

Promote a shared reference vocabulary
MOONLIB-W05 | Roadmap scope. Two real products need the same company task source or artifact reference
1. Document the two consumer jobs and existing local shapes
2. Separate stable identity fields from product-owned policy
3. Define a versioned shared reference and compatibility rules
4. Migrate a producer and receiver using preserved fixtures
5. Replay prior records and verify exact linkage without conflating domain states
Edge case Similar field names may conceal different domain meanings; a proposed common shape must be rejected if it erases an important distinction.
Failure and recovery A failed migration keeps the previous supported contract available and leaves records unmigrated rather than silently relabeling identities.
Acceptance Use two actual consumers, a representative historical fixture and a changed-version fixture; verify source and artifact links remain exact through forward migration and supported replay.

The correct success measure is fewer identity and compatibility mistakes at real handoffs, not a larger common package. Shared utilities should be promoted because they remove repeated semantic work from two consumers. A single product’s future wishes are too weak a basis for a stable shared contract.
The four passing pipeline tests demonstrate a useful bounded contract surface. They do not establish that MoonProj, MoonBook and MoonDesk refer to the same company or artifact in a live journey. The PRD is stronger when that integration is a separate milestone with exact readback and historical replay.
Local DTOs and explicit adapters are often better than a common type. If two products use the same word for different concepts, centralization can make mistakes easier to compile. MoonLib should preserve reference kinds and require a semantic justification for every shared field, especially status or authority fields.
The next iteration should choose one source or artifact handoff, inventory only the fields that must survive it, and qualify two consumers on the resulting versioned vocabulary. Broader company and customer models can wait. Multi-target release evidence should then support the exact published surface rather than a general claim that every package is portable.
