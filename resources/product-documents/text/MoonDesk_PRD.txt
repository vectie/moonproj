MoonDesk product requirements
OPC OS portfolio  |  30 September 2026  |  Version 1 for product review
MoonDesk should be the human inspection and intervention workbench for sources, files and agent output. The verified local web path demonstrates bounded browsing and document-selection continuity. Native desktop distribution, long-lived sessions and broad host integrations remain separate qualification work.
Repository maturity claim local single-user alpha
This document defines the product baseline and a separately proposed roadmap. Acceptance tests below are release criteria unless a cited observation explicitly says they passed. Current source coverage does not establish production deployment or customer value.
Product philosophy and scope
The founder needs to open the exact artifact, see what changed and decide what to accept. MoonDesk should preserve the current commitment context while exposing supported file actions and honest dependency states. It should not create a second company ledger or duplicate the accepted knowledge store.
Progressive disclosure is a product requirement: browse, inspect and review come first. Code editing, Office editing, graphs and domain packs appear when the task and installed capabilities need them. A rich desktop shell only creates leverage when it lowers the time and confusion between a work result and a human decision.
Users and jobs
human workspace operator
Locate the correct workspace item and choose a supported action.
Trigger A file, inbox item or favorite needs inspection or an edit.
Successful outcome The selected path and context persist, and unsupported actions are explicit.
founder inspecting work
Inspect the exact output of a company commitment and resolve the next review decision.
Trigger A produced artifact or unresolved discrepancy is ready for human attention.
Successful outcome The founder sees source, criterion, file version and blocker in one context.
reviewer editor
Compare and safely edit supported content, then record a bounded review.
Trigger A document requires correction or an external edit creates a conflict.
Successful outcome Save and apply preserve original bytes and make review scope unambiguous.
pack application user
Use a domain pack through its genuine configured host surface.
Trigger A task needs a specialist capability beyond generic file inspection.
Successful outcome Installed capabilities and authority are clear, with domain meaning owned by the pack.

User scenarios
Workspace browse search favorites inbox preview
MOONDESK-UC01 | Baseline scope. Find and inspect a real workspace file.
1. Browse or search the workspace using favorites or inbox context.
2. Select the real file and show a supported preview rather than an unrelated empty workspace.
3. Navigate or reload while retaining the supported selected document path.
Edge case Markdown must not offer an unsupported Wiki document action; DOCX selection uses the supported route.
Failure and recovery Missing or moved files yield a clear unavailable state and preserve the surrounding workspace context.
Acceptance Reproduce the web Markdown and DOCX paths; supported DOCX selection persists after handoff and reload.
Evidence references README.mbt.md; docs/PRODUCT_CONTRACT.md#Capability status
Direct code and bounded DOCX XLSX PPTX editing with review compare
MOONDESK-UC02 | Baseline scope. Edit a supported code or Office document safely.
1. Open a file whose format and feature subset are supported.
2. Edit with semantic changes and compare the result against the saved version.
3. Validate apply, save and reload while preserving conflicts and unsupported content.
Edge case An unsupported Office feature cannot be silently discarded or presented as faithfully editable.
Failure and recovery External modification creates a recoverable conflict; failed apply leaves the original file intact.
Acceptance For code and supported DOCX/XLSX/PPTX fixtures, verify save/reload, diff and conflict preservation separately.
Evidence references docs/PRODUCT_CONTRACT.md#Capability status; docs/EXECUTABLE_DOCUMENT_UX.md
MoonWiki MoonCode sessions and MoonClaw review control
MOONDESK-UC03 | Baseline scope. Review runtime work and durable book state.
1. Open the projected MoonBook or MoonClaw journal for the selected work.
2. Use configured service descriptors to launch optional sessions or sidecars.
3. Inspect run results and return a bounded review decision to the owning service.
Edge case Selecting a service or viewing a journal does not grant new execution authority.
Failure and recovery An absent sidecar remains unavailable with a repairable configuration message; the shell must not simulate a running session.
Acceptance A configured host round-trip demonstrates that Desk projects Book truth and Claw state without taking ownership of either.
Evidence references README.mbt.md; README.md#Optional MoonTown Service

1. Search files, code, book knowledge, tasks, runs, reviews and artifacts.
2. Add only the selected material to a document conversation or anchored discussion.
3. Recover the thread within its documented local or server boundary.
Edge case A changed artifact needs a stale-anchor warning rather than attaching old comments to unrelated new content.

Published Work graph composition and MoonFlow import
MOONDESK-UC05 | Baseline scope. Compose and import a Published Work graph.
1. Select nodes from the exact capability catalog and validate schema versions.
2. Check adapter health, compatibility and required authority before import.
3. Import the declared graph into MoonFlow and show pending review or execution state.
Edge case Catalog inventory or selection alone does not establish installed health or permission.
Failure and recovery Incompatible, unhealthy or unauthorized nodes block activation and identify the offending edge or capability.
Acceptance A valid graph imports only after all checks; fixture-only graph rows cannot appear executable.
Evidence references docs/PRODUCT_CONTRACT.md#Capability-truth rule
Evidence Watch and Work Package export
MOONDESK-UC06 | Baseline scope. Watch evidence and export a reviewable work package.
1. Configure the source and purpose of an Evidence Watch through its wizard.
2. Provision the owning Book/Town records and inspect the resulting watch status.
3. Export visible work, reviews, sources and warnings as an HTML Work Package.
Edge case Export must not include hidden reasoning, credentials or material outside the selected package.
Failure and recovery A partially configured watch remains incomplete; missing evidence in an export stays visible as a warning.
Acceptance An exported package opens independently with its visible evidence and warnings; the watch names its actual owning service.

Data state and authority
Workspace files and edit sessions
Owner Filesystem owner; Desk owns the local interaction and edit session
State model Selected, previewed, edited, validated, saved, conflict or recovery needed
Write authority File write permissions and chosen apply action bound edits
Retention and recovery Keep originals and recoverable edit history where supported; do not equate preview cache with source
Review and conversation projection
Owner Owning Book, Claw or domain service; Desk owns UI anchors
State model Loaded, locally drafted, submitted, confirmed or stale
Write authority Named reviewer approves only exact artifact and allowed operation
Retention and recovery Persist according to declared local/server mode and expose incomplete recovery
Work graph and package
Owner Desk composition with MoonFlow lifecycle ownership
State model Draft graph, validated import, pending review, activated elsewhere; package exported
Write authority Catalog selection confers no runtime authority
Retention and recovery Keep exact catalog/version references and visible export warnings
Interfaces and handoffs
MoonBook and MoonClaw
Payload Book projections, run journals, review controls and session references
Contract Desk is the human surface, not accepted-knowledge or model-runtime owner
Failure behavior Unavailable services retain clear status and do not become synthetic local truth
MoonLeaf and MoonEdit
Payload Supported file sessions, operations, validation and conflict records
Contract Core format/editor contracts define supported edits; host UX requires separate acceptance
Failure behavior Unsupported operations fail safely and preserve file bytes
MoonFlow and domain packs
Payload moonsuite.work-model.v1 and moonflow.capability-catalog.v1 graph payloads
Contract Exact schema, version, authority and healthy adapter match are all required
Failure behavior Reject incompatible nodes before activation; domain packs provide their own domain UI

Delivery roadmap
Phase 1 Qualify the baseline
Reproduce the product's critical local, contract and configured paths with exact versions and observable receipts. Close missing prerequisites without widening authority.
Requirements MOONDESK-B01, MOONDESK-B02, MOONDESK-B03, MOONDESK-B04, MOONDESK-B05, MOONDESK-B06
Exit gate Every P0 baseline acceptance has an explicit result and evidence locator; unresolved dependency and integration states remain visible.
Phase 2 Complete one connected outcome
Implement the smallest useful cross-product scenario and test review, interruption and recovery with real authorized inputs.
Requirements MOONDESK-R01, MOONDESK-R02
Exit gate A named user accepts the exact output and can recover its evidence chain without reconstructing identities manually.
Phase 3 Expand only after measured value
Add remaining proposed workflows where observed use demonstrates reduced coordination cost or a distinct required capability.
Requirements MOONDESK-R03
Exit gate Measure the outcome against the simpler alternative, include review overhead, and retain the ability to stop or narrow low-value scope.

Alternatives and optimality
File manager plus existing editor
Advantage Familiar tools and low onboarding cost
Cost Cross-app evidence and review context can be lost
When to choose Use for isolated files if Desk cannot reduce inspection time
Each domain app with its own review surface
Advantage Preserves specialist workflow and terminology
Cost Repeated navigation and inconsistent review state increase burden
When to choose Prefer for deep domain operations; keep Desk as a common inspection entry rather than replacing every app
A human evidence workbench is a clear role, but feature breadth currently risks overwhelming the beginning founder. The proposed commitment workspace is worthwhile if it measurably reduces wrong-file review and context reconstruction.
The PRD should gate each host path independently. A stable editor core, web preview and native app have different acceptance obligations. Clean-machine native installation and lifecycle recovery are prerequisites to a mature desktop claim.
Keep advanced graph composition behind installed-capability evidence. A simple browse-to-review path with precise errors is more useful than a complete-looking canvas that cannot actually run.
Open product decisions
Decision Which three actions belong on the default founder surface?
Recommendation Start with browse source, inspect result and resolve review; reveal specialist actions contextually.
Consequence Exposing every mode at first run increases learning cost without proving value.
Decision What is the first native desktop release gate?
Recommendation Require clean-machine launch, supported file selection, save/reload and interruption recovery before a native maturity claim.
Consequence The prior permission-denied launch leaves native UX unqualified rather than disproven.
