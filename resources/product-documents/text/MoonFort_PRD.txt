MoonFort product requirements
OPC OS portfolio  |  30 September 2026  |  Version 1 for product review
MoonFort is an execution authority boundary for operators and MoonClaw hosts. The frozen baseline covers profile preflight, trusted single-use approval grants, supervised local backends, a fail-closed AEN backend contract, scratch evidence and reviewed artifact promotion. Eight native command-preflight tests passed. No complete Firecracker or AEN deployment, hostile-host trial or production arbitrary-code containment was established. The next product milestone is a clearly scoped approved action whose refusal or completion receipt returns to its task, followed by a separately reviewed artifact promotion. Founder-facing UI belongs in the requesting host.
Repository maturity claim local supervised backends and fail-closed AEN contract; production qualification outstanding
This document defines the product baseline and a separately proposed roadmap. Acceptance tests below are release criteria unless a cited observation explicitly says they passed. Current source coverage does not establish production deployment or customer value.
Product philosophy and scope
Approval must identify the actual authority being granted: readable and writable locations, executable tools, network scope and resource limits. A caller should not be able to turn approval for one bounded action into a weaker backend or broader profile. Refusal is a legitimate outcome when the required enforcement is unavailable. An apparently successful process is not a safe result if the system cannot say which restrictions were enforced and which were degraded.
MoonFort supports the approved-execution step of accountable work. MoonClaw owns task execution coordination; MoonDesk owns workspace presentation; domain products own commitments and durable knowledge. MoonFort contributes constrained process execution and evidence. Scratch output is not automatically an accepted artifact, and a retained receipt is not customer acceptance. The human should see intelligible authority, results and promotion choices without needing to operate sandbox internals every day.

User scenarios
Preflight a trusted one shot action
MOONFORT-W01 | Baseline scope. MoonClaw submits an opaque approval identifier
1. Resolve the trusted single-use grant
2. Select executor-owned paths, tool policy and resource profile
3. Preflight the command against that profile
4. Consume the grant according to its single-use contract
5. Return refusal or an execution-bound receipt
Edge case A caller supplies a profile or backend override; it cannot weaken the executor’s trusted choice.
Failure and recovery Missing, invalid or already consumed approval refuses execution and must not start an unsandboxed process.
Acceptance Run valid and invalid preflight fixtures, replay a consumed grant and attempt a caller downgrade; verify no unauthorized execution begins.
Evidence references README.mbt.md#Current status; docs/EXECUTION_BOUNDARY_GUARD.md; moon-luna-investigation-ledger-20260930.md
Run in a supervised local backend
MOONFORT-W02 | Baseline scope. An approved action selects a qualified local macOS or Linux profile
1. Create private workspace and scratch boundaries
2. Apply the supported sandbox-exec or bubblewrap controls
3. Run with declared network, process, resource and output restrictions
4. Collect termination status and enforcement evidence
5. Retain output and scratch inventory for inspection
Edge case Shared-kernel limitations or incomplete aggregate quota enforcement must be visible in the claim level.
Failure and recovery Backend setup failure refuses rather than running on the host without the requested boundary.
Acceptance On each supported host, test allowed access, denied access, network refusal, timeout and excessive output; label controls only as strongly as observed enforcement permits.
Evidence references README.mbt.md#Current status; docs/LOCAL_BACKEND_EVIDENCE.md
Require the strict AEN backend
MOONFORT-W03 | Baseline scope. A workload requires stronger arbitrary-code containment
1. Resolve the approved strict backend requirement
2. Validate the required attested deployment and provisioner contract
3. Run only if qualification and deployment prerequisites are met
4. Return evidence associated with the strict execution boundary
Edge case An available local backend is weaker than the requested strict profile and is not an acceptable substitute.
Failure and recovery Missing attestation, deployment or required enforcement produces a precise refusal with no host fallback.
Acceptance Remove a strict prerequisite and verify refusal. A positive production claim requires independent microVM qualification, not a unit test or local substitute.

Retain scratch artifacts and inspect promotion
MOONFORT-W04 | Baseline scope. A bounded process exits with output or workspace changes
1. Inventory scratch changes and compute fingerprints or digests
2. Retain large output in an artifact spool rather than relying on a truncated screen
3. Associate evidence with the execution receipt
4. Present candidate changes for a separate reviewed promotion
5. Recheck fingerprints before applying selected changes
Edge case The destination changed since review, or scratch bytes differ from the inspected fingerprint.
Failure and recovery A stale fingerprint or unapproved change blocks promotion; canonical MoonBook files are never bulk copied back as a shortcut.
Acceptance Review a selected artifact, change its bytes and verify refusal; retry with a newly inspected matching artifact and retain the source execution evidence.
Evidence references README.mbt.md#Current status; docs/PROMOTION_RECOVERY_INSPECTION.md
Approve a bounded action from a task
MOONFORT-W05 | Roadmap scope. A MoonProj or MoonClaw task requests consequential delegated work
1. Show file, network, tool and budget scope in the requesting host
2. Record the named approval for that bounded request
3. Submit only the trusted approval identifier
4. Receive a denial or completion receipt
5. Read the receipt back from the originating task
Edge case The request changes after approval; the existing grant cannot authorize new scope.
Failure and recovery Disconnected receipt delivery remains pending and can retry without replaying the process.
Acceptance A host tester approves and denies otherwise identical tasks; each returns a precise linked receipt, and retrying receipt delivery does not execute again.
Evidence references docs/EXECUTION_BOUNDARY_GUARD.md; Recommended founder approved bounded action
Promote only the reviewed artifact
MOONFORT-W06 | Roadmap scope. A named reviewer accepts a specific scratch result for durable use
1. Open the retained artifact and its origin receipt
2. Select the exact files or changes to promote
3. Review destination conflicts and digests
4. Authorize promotion of that selection
5. Confirm destination readback and record the promotion outcome
Edge case Unselected changes or unknown side effects remain in scratch even if one artifact is accepted.
Failure and recovery Interrupted promotion requires inspection of actual destination state before recovery; an uncertain result cannot be called complete.
Acceptance Qualify selective promotion, changed destination, interrupted write and recovery; only the inspected matching selection reaches the durable workspace.
Evidence references docs/PROMOTION_RECOVERY_INSPECTION.md; Recommended review before promotion

No process execution
Advantage Smallest security surface for read only tasks
Cost Cannot complete tasks needing tools or generated artifacts
When to choose Prefer whenever the task can be fulfilled without running a process
Supervised local backend
Advantage Practical bounded execution on supported hosts
Cost Shared-kernel limitations and deployment-specific evidence
When to choose Use only within its declared qualified scope
Independently qualified microVM service
Advantage Stronger isolation appropriate to untrusted workloads
Cost Attestation deployment operations and audit cost
When to choose Require for production arbitrary-code claims rather than relabeling a local backend
A useful sandbox product is defined by what it can refuse and prove, not by how often it launches a process. Keeping the approval-ID-only interface and executor-owned profiles reduces the number of places that can expand authority. Adding convenience overrides would undermine the main value of the component.
The strongest evidence currently covers preflight, not complete containment. The PRD must retain that distinction even when local backends are useful for supervised work. A security label should refer to specific enforced controls on a qualified deployment, never to an undifferentiated passing test count.
A simpler no-execution path is optimal for read-only requests that do not need tools. For trusted bounded development work, a declared local backend may be adequate. For arbitrary untrusted workloads, the additional microVM qualification cost is justified; a weak fallback is not an acceptable optimization.
The roadmap can become narrower by qualifying one task type, one backend and one artifact promotion route before widening host support. That slice should include denial, changed scope, retained output and interrupted promotion. It proves the full authority boundary while avoiding a founder-facing control panel full of backend mechanics.
