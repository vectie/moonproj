MoonEdit product requirements
OPC OS portfolio  |  30 September 2026  |  Version 1 for product review
MoonEdit is an alpha, host-independent text and code editing core. Its frozen baseline is deterministic in-memory editing, UTF-16 positions, selections, revisions, bounded undo and redo, a host effect protocol, merge receipts and typed language-service lanes. Nine JavaScript core editor tests passed; those results do not establish file persistence, large-file performance, actual language-server transport or a usable conflict-choice interface. The recommended next slice is one MoonDesk edit, conflict, reviewed save and reopen journey. There is no separate MoonEdit application roadmap.
Repository maturity claim editor-core alpha
This document defines the product baseline and a separately proposed roadmap. Acceptance tests below are release criteria unless a cited observation explicitly says they passed. Current source coverage does not establish production deployment or customer value.
Product philosophy and scope
An editor should protect the difference between a user’s working text, an external file version and a suggestion that has not been accepted. MoonEdit makes those distinctions explicit in its state and effects. Determinism allows the same edit history to be explained and tested; revision binding prevents a delayed host response from silently changing a newer document. A successful core transition does not mean bytes reached durable storage.
The library contributes to the inspected-artifact part of accountable work. MoonDesk owns the user’s file picker, filesystem access, save destination, persistence and visible conflict choices. Other systems own agent execution and knowledge acceptance. MoonEdit should allow a founder to refine a deliverable through the host without granting an agent ownership of the document or treating saved prose as verified company truth.

User scenarios
Edit and navigate the text revision
MOONEDIT-W01 | Baseline scope. A host sends an edit command or selection change
1. Validate UTF-16 positions against the current document
2. Apply the edit atomically and advance the revision
3. Update selections using the defined position rules
4. Record bounded undo history and allow redo after undo
Edge case A selection crosses a surrogate pair boundary or an edit targets a stale revision; the core must enforce its position and revision contract.
Failure and recovery Invalid edits return an explicit result without partial text mutation or inconsistent selection.
Acceptance Apply insertion, replacement and deletion to mixed Unicode text; undo and redo within the declared history bound restore the expected text and selection.
Evidence references docs/PRODUCT_CONTRACT.md#Capability status; README.mbt.md; moon-luna-investigation-ledger-20260930.md
Save load and reload through the host
MOONEDIT-W02 | Baseline scope. The user requests persistence or the host discovers a new file version
1. Core emits a typed effect request
2. Host performs the filesystem operation with its own permission checks
3. Host returns a callback bound to request, revision and file version
4. Core accepts only the matching response and exposes the resulting state
Edge case Two saves complete out of order, or reload arrives after a newer local edit.
Failure and recovery Failed or stale callbacks cannot clear newer dirty state; the host retains a retryable error and working text.
Acceptance Delay revision A save until after revision B exists; acknowledge A and verify B still needs saving. Reopen only after a matching successful save acknowledgement.
Evidence references docs/PRODUCT_CONTRACT.md#Host contract
Merge concurrent edits with a receipt
MOONEDIT-W03 | Baseline scope. Local text and an externally changed version share an earlier base
1. Identify base, local and external revisions
2. Compose nonoverlapping changes where the contract is unambiguous
3. Preserve ambiguous overlap in a conflict receipt
4. Let the host show choices and apply the explicitly selected result
Edge case An agent suggestion overlaps a manual edit; a proposal cannot count as human acceptance.
Failure and recovery Missing base or invalid revision binding leaves the merge unresolved and retains both candidate texts.
Acceptance Use disjoint changes, identical edits and conflicting overlap fixtures; prove that only the first qualified cases compose automatically and the overlap remains reviewable.
Evidence references docs/MERGE_CONTRACT.md; docs/PRODUCT_CONTRACT.md#Capability status
Coordinate language service results
MOONEDIT-W04 | Baseline scope. The host requests semantic tokens, completion or a definition
1. Send a typed request for the current document context
2. Let the host own transport and service lifecycle
3. Receive a response with the originating context
4. Apply only a still relevant response or discard it with a diagnostic
Edge case A completion response arrives after the user has changed the document or closed it.
Failure and recovery Unavailable language service leaves ordinary editing usable; transport failure is not a document load failure.
Acceptance Exercise the three typed lanes with fixture responses, including stale and missing replies. Treat a fixture success separately from actual LSP transport qualification.
Evidence references docs/PRODUCT_CONTRACT.md#Capability status
Save a conflict safe deliverable in Desk
MOONEDIT-W05 | Roadmap scope. An author edits a customer deliverable that also changes externally
1. Open the file with a known external version
2. Make a local edit and encounter the changed external version at save
3. Inspect the exact conflicting spans and preserve alternatives
4. Choose the merged result explicitly
5. Save and reopen the acknowledged revision, retaining a conflict receipt
Edge case The application closes after conflict choice but before save acknowledgement; recovery must not imply a completed save.
Failure and recovery Storage denial or version race leaves the author’s working text recoverable and the original external file untouched by an unapproved overwrite.
Acceptance Run a real MoonDesk journey with injected external change, failed first save, retry and reopen; compare saved bytes and the chosen revision.
Evidence references docs/PRODUCT_CONTRACT.md#Host contract; docs/MERGE_CONTRACT.md

The central product risk is a boundary failure between deterministic core state and asynchronous storage, not a shortage of editing commands. A smaller set of reliable edit, save and merge operations is more useful than broad language features if users can trust that no stale callback will erase their latest work.
A library-level PRD is appropriate because integrations own the user’s actual experience. The nine passing core tests should remain a narrow maturity statement. Measuring core correctness separately from host recovery and conflict usability prevents an alpha core from being advertised as a finished editor.
For a single small notes field, a native text widget is better: less state to synchronize and fewer dependencies. MoonEdit earns adoption when the host needs revisioned effects, explainable concurrent edits or portable core behavior across targets. Those needs should be demonstrated rather than assumed from portfolio membership.
The PRD can be improved by naming one document size envelope and one host storage implementation before adding general LSP transport. Qualification should first prove a realistic deliverable can survive an external edit and failed save. Richer services can then reuse a stable document lifecycle rather than adding another source of stale state.
