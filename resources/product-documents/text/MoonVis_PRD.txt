MoonVis product requirements
OPC OS portfolio  |  30 September 2026  |  Version 1 for product review
MoonVis should remain an internal design-token, asset-lineage and visual-guidance pack. Its frozen baseline covers versioned marks and variants, a handbook, deterministic token and asset-bundle resolution, a MoonFlow adapter and a Rabbita bundle inspector. Four JavaScript token-resolution tests passed. No cross-product browser visual review, final composited accessibility proof or public asset-redistribution approval was established. The next useful outcome is two consuming products using the same versioned status and evidence token meanings while retaining their own task-specific interaction and layout.
Repository maturity claim executable local pack
This document defines the product baseline and a separately proposed roadmap. Acceptance tests below are release criteria unless a cited observation explicitly says they passed. Current source coverage does not establish production deployment or customer value.
Product philosophy and scope
Visual consistency should help users recognize an action or state correctly. A familiar color or mark is harmful if it makes a draft look approved, an internal success look customer accepted or an unavailable route look ready. MoonVis should give products stable visual vocabulary, explicit usage limits and provenance, while leaving the product owner responsible for whether a particular state is true. A design system can communicate evidence quality; it cannot create that evidence.
The customer is a designer, UI engineer or asset reviewer integrating a product. A founder benefits through clearer controls in MoonProj, MoonDesk or MoonFind and should not need another daily visual-management application. In the operating sequence, MoonVis helps people inspect source, decision and execution states without confusing them. It does not own commitments, runtime authority, artifact acceptance, cash receipt or reviewed learning. The consuming product’s named acceptance is the final usability gate.

User scenarios
Select versioned marks and visual guidance
MOONVIS-W01 | Baseline scope. A designer needs a mark variant or product adaptation
1. Locate the source mark and its versioned variants
2. Read the relevant handbook and adaptation guidance
3. Inspect lineage and recorded rights decisions
4. Select a variant suited to the intended product and channel
5. Retain the asset reference and any limits with the adoption record
Edge case A desired channel or redistribution use is outside the recorded rights decision.
Failure and recovery Missing provenance or unresolved rights prevents an unrestricted-use claim; the product cannot infer permission from the asset being present.
Acceptance Trace a selected export to its source version and usage guidance; flag an unsupported channel and retain the original source reference.
Evidence references docs/PRODUCT_CONTRACT.md#Capability status; README.md
Resolve a deterministic visual bundle
MOONVIS-W02 | Baseline scope. A product requests a token and asset bundle
1. Construct moonvis/visual-asset-bundle-request@1.0.0
2. Resolve the requested versions and channel
3. Emit moonvis/visual-asset-bundle-manifest@1.0.0 with content address
4. Include token and asset versions contrast expectation drift and limitations
5. Materialize only the manifest within the granted workspace-mutation scope
Edge case A token version or asset variant is unavailable, or requested adaptation drifts from the expected bundle.
Failure and recovery Resolution returns a precise limitation or failure rather than silently replacing the requested version or claiming a completed product UI.
Acceptance Resolve identical supported input twice and compare output identity; test missing version and drift cases and verify all limitations remain in the manifest.
Evidence references docs/PRODUCT_CONTRACT.md#Adoption contract; moon-luna-investigation-ledger-20260930.md
Inspect and reconcile a local bundle
MOONVIS-W03 | Baseline scope. MoonFlow invokes bundle resolution or a reviewer opens the Rabbita inspector
1. Invoke moonvis/visual.asset-bundle.resolve@0.1.0 with the exact request
2. Reconcile the local operation result and its manifest
3. Expose health for the supported local capability
4. Inspect the resolved assets and limitations in the bundle UI
Edge case A healthy local capability may still produce a bundle unsuitable for a particular consuming product.
Failure and recovery Failed invoke or incompatible output blocks successful reconciliation; the inspector cannot substitute for a product-specific acceptance test.
Acceptance Use a supported local invocation and an invalid request, then inspect the manifest. Verify health and result status remain distinct from adopted UI readiness.
Evidence references docs/PRODUCT_CONTRACT.md#Capability status; docs/PRODUCT_CONTRACT.md#Adoption contract
Adopt consistent founder controls
MOONVIS-W04 | Roadmap scope. MoonProj MoonDesk or MoonFind needs common status and evidence semantics
1. Choose two products and identify concrete overlapping controls
2. Agree token meanings without merging their domain lifecycles
3. Import a shared versioned bundle without copying token values
4. Adapt layout to each task and inspect final composited pixels
5. Run interaction visual-regression and contrast checks
6. Record named product acceptance and manifest linkage
Edge case The same visual token would imply different domain meanings in the two products; adapt the mapping or keep separate tokens rather than forcing uniform appearance.
Failure and recovery An inaccessible combination, copied token drift or unclear state label blocks adoption even when bundle resolution succeeds.
Acceptance Two real products demonstrate matching intended meanings, correct task-specific behavior, accessible composited contrast and traceable manifest versions across an update.
Evidence references docs/PRODUCT_CONTRACT.md#Adoption contract; Recommended consistent founder controls

When to choose Do not expand MoonVis into this role without separately proven product demand
MoonVis has a clear reason to exist when a product can answer which token and asset version produced its visible controls. A deterministic bundle and content-addressed manifest make that answer inspectable. Broadening into a UI generator would weaken the boundary between visual inputs and the product’s responsibility for meaningful interaction.
The four token tests are library evidence. They cannot demonstrate contrast after transparency and compositing, keyboard focus behavior or whether a founder mistakes an approved task for customer-accepted work. The next acceptance evidence must come from actual host pixels and task scenarios rather than additional token snapshots alone.
A static style guide is often sufficient for one product with infrequent changes. Programmatic resolution earns its cost when two products share assets or semantics and need reproducible updates. The adoption milestone should therefore be two concrete products, not a mandate to redesign the whole portfolio.
The PRD can narrow the first shared-control slice to a small set of overlapping status and evidence indicators in MoonProj and one host. Layout and domain-specific actions should remain local. Once provenance, drift detection and rollback work on that slice, additional products can adopt the same contract with independent acceptance.
