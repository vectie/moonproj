MoonFlow product requirements
OPC OS portfolio  |  30 September 2026  |  Version 1 for product review
MoonFlow is a durable, non-agent orchestration engine for declared work. Its baseline imports exact capability contracts, advances dependency-ready attempts when invoked, records authority and adapter evidence, and preserves review and recovery across revisions. It does not reason about objectives or run an autonomous scheduling loop. The recorded acceptance-review tests establish a small local contract; a complete external adapter journey, restart recovery and company-task receipt return still need qualification.
Repository maturity claim local alpha
This document defines the product baseline and a separately proposed roadmap. Acceptance tests below are release criteria unless a cited observation explicitly says they passed. Current source coverage does not establish production deployment or customer value.
Product philosophy and scope
Declared work should be understandable before it can execute. A graph names operations, dependencies, allowed authority and evidence expectations; the engine advances only what those declarations permit. An installed product or a visible graph node is insufficient proof of capability. Exact manifests, adapter declarations and current health must agree before work becomes executable.
The engine converts approved execution into inspectable attempts and reviewable outputs. It owns neither the intent behind a source nor the external effect of an adapter. Keeping those distinctions explicit permits a founder or operator to see what actually happened while retaining separate authority over artifact acceptance, customer acceptance and payment. Durable bookkeeping is useful only if it lowers the effort needed to close that handoff.

User scenarios
Import a conformant work graph
MF-W01 | Baseline scope. An operator imports a graph and capability source bundle
1. Read the manifest, host adapter declaration and expiring health
2. Compile moonflow.capability-source-bundle.v1 into moonflow.capability-catalog.v1
3. Resolve product/tool@pack-version and product/schema@schema-version
4. Refuse the graph if operation, schema, authority or claim differs
Edge case An installed but unhealthy operation can remain discoverable while unavailable for execution.
Failure and recovery A partial import must not leave executable nodes using stale catalog data.
Acceptance Import a matching fixture; independently change each contract dimension and require a precise refusal with zero dispatched attempts.
Evidence references docs/PRODUCT_CONTRACT.md#Adapter contract; docs/CAPABILITY_TRUTH.md
Advance dependencies and attempts on invocation
MF-W02 | Baseline scope. A host explicitly asks the engine to advance eligible work
1. Load the canonical graph revision and event stream
2. Identify satisfied dependencies and required authority decisions
3. Create idempotent attempts for eligible operations
4. Return events and blockers to the invoking host
Edge case A graph with unmet dependencies remains waiting; the engine does not invent work to make progress.
Failure and recovery If an invocation repeats after timeout, recover the same attempt rather than scheduling a duplicate.
Acceptance A diamond graph advances only satisfied nodes; duplicate invocations and revoked authority do not produce unauthorized attempts.
Evidence references README.mbt.md#Constitutional boundary; docs/PRODUCT_CONTRACT.md#Capability status
Execute reconcile and review adapter results
MF-W03 | Baseline scope. A dependency-ready authorized attempt is dispatched
1. Send the canonical input and correlation identity to its product adapter
2. Record the adapter-owned receipt and output references
3. Request reconciliation for an uncertain external outcome
4. Present the exact output for explicit review
Edge case An adapter success is execution completion, not accepted work.
Failure and recovery An unresolved effect remains unknown; a review rejection produces revision work rather than erasing the original receipt.
Acceptance Exercise success, mismatched receipt, unknown outcome, accepted review and rejected review with preserved history.
Evidence references README.mbt.md#Adapter contract; docs/PRODUCT_CONTRACT.md#Adapter contract
Revise and recover work without rewriting history
MF-W04 | Baseline scope. A reviewer requests changes or the engine restarts
1. Create a child revision referencing its parent
2. Retain accepted evidence and explicitly eligible reusable checkpoints
3. Replay the event stream to reconstruct pending attempts
4. Reconcile uncertain effects before retry
Edge case Changing input, authority or capability version can invalidate reuse even when a node name is unchanged.
Failure and recovery A damaged or incomplete checkpoint must be refused with an actionable restore path, not silently treated as current.
Acceptance Restart after receipt persistence and after dispatch; both recover the same history, and a child revision never mutates accepted parent outputs.
Evidence references README.mbt.md#Event stream v3; docs/PRODUCT_CONTRACT.md#Persistence and recovery
Inspect work through CLI and host canvas
MF-W05 | Baseline scope. An operator or reviewer opens a published work graph
1. Load the graph, catalog and configured runtime
2. Project node status and exact latest attempt
3. Expose blocker, authority decision, receipt and review history
4. Allow supported operator actions through the same engine contract
Edge case An unconfigured canvas is an unavailable projection, not proof that the operations can execute.
Failure and recovery If projection data is stale, show the age and stop unsafe actions until canonical state reloads.
Acceptance Compare CLI and host views against one event fixture; no view may imply acceptance for unreviewed success.
Evidence references README.mbt.md#CLI; docs/PRODUCT_CONTRACT.md#Capability status
Reconcile company task and work packet
MF-W06 | Roadmap scope. MoonProj supplies a signed approved work item
1. Validate the task identity, approval revision and bounded work declaration
2. Bind one immutable graph revision to that task
3. Return attempts, artifacts and review receipts with the original identity
4. Resume receipt delivery after restart or receiver outage
Edge case A revised company task creates a revised binding instead of modifying an already approved graph invisibly.
Failure and recovery Failed receipt return is a pending reporting handoff, not permission to repeat an adapter effect.
Acceptance A signed synthetic task survives interrupted dispatch, engine restart and delayed receipt return with one graph binding.
Evidence references moon-luna-investigation-ledger-20260930.md; docs/PRODUCT_CONTRACT.md#Persistence and recovery
Minimal status for the accountable owner
MF-W07 | Roadmap scope. A founder needs the next action on delegated work
1. Summarize current outcome, next decision or blocker in ordinary language
2. Link the exact artifact and evidence behind the summary
3. Keep graph terminology available as advanced detail
4. Distinguish internal review, customer acceptance and cash receipt
Edge case Multiple blockers must preserve their order and ownership instead of collapsing into one misleading progress label.
Failure and recovery A stale summary must not announce completion after a graph revision invalidates the result.
Acceptance Test representative waiting, unknown, failed and review-ready states; the owner identifies who must act and why.
Evidence references docs/PRODUCT_CONTRACT.md#Capability status; moon-luna-investigation-ledger-20260930.md

Alternatives and optimality
A script with a manifest and manual checklist
Advantage Easy to understand for a short linear process
Cost Weak recovery and duplicated evidence collection at scale
When to choose Prefer for one-off reversible work without external uncertainty
An established generic workflow engine
Advantage Mature scheduling and operational tooling
Cost Requires adapting MoonSuite exact capability, authority and review semantics
When to choose Benchmark integration effort before claiming a bespoke engine is superior
The non-agent boundary is a strong design choice because dependency progression and evidence replay benefit from deterministic behavior. It is not evidence that the implementation is optimal. A standard workflow engine with a thin authority and review layer may achieve the same user outcome at lower maintenance cost.
The PRD should prefer one complete external adapter journey over broad nominal catalog coverage. Import, execution, receipt correlation, review rejection, revision and restart belong in the same qualification scenario. Isolated acceptance tests cannot establish that entire chain.
A narrower first release could offer CLI inspection and a minimal host status projection before investing in a rich canvas. Operators need to understand the next safe action; visual graph density is not itself a measure of reduced coordination.
Future task integration is valuable only if exact receipts return to the originating commitment after failures. It should not import company decision rules into the engine. A completed work graph can support artifact inspection, while separate customer acceptance and cash evidence stay in their owning records.
