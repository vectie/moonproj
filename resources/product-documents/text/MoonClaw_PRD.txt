MoonClaw product requirements
OPC OS portfolio  |  30 September 2026  |  Version 1 for product review
MoonClaw is the shared execution runtime for application hosts and operators. Its frozen baseline covers planned sessions, durable jobs, workspace and journal records, operator controls, capability dispatch, and recovery. It supplies a bounded execution record to other products; it does not decide company strategy or certify customer acceptance. Local job and native-suite evidence is substantial, but configured provider execution, remote agents, live company-task binding, clean-machine installation and multi-day recovery remain separate release gates.
Repository maturity claim advanced local alpha
This document defines the product baseline and a separately proposed roadmap. Acceptance tests below are release criteria unless a cited observation explicitly says they passed. Current source coverage does not establish production deployment or customer value.
Product philosophy and scope
A useful run begins with a comprehensible objective, permitted sources, named authority and a stop condition. The runtime should make those constraints enforceable at the moment of execution, rather than treating an earlier conversation as unlimited permission. Each model or tool action must remain attributable to a job and reviewable afterward. More actions, longer sessions and autonomous continuations are not success measures.
MoonClaw occupies the approved-execution and inspected-artifact part of an accountable work cycle. MoonProj retains company commitments, MoonFlow retains declared dependencies, MoonGate retains provider policy, and MoonBook retains reviewed knowledge. A runtime memory entry or successful execution receipt cannot silently cross these ownership boundaries. The best integration returns enough evidence for a human to decide whether the intended result was delivered.
Users and jobs
Runtime operator
Start, diagnose, steer and safely stop durable jobs
Trigger A host submits approved work or a run becomes interrupted
Successful outcome The operator knows what executed and can recover without duplicate external effects
Application host integrator
Expose sessions, artifacts and controls through a product interface
Trigger A product needs model-assisted work beyond a single synchronous request
Successful outcome Stable runtime identities and honest states survive host reload
Capability adapter author
Provide a versioned operation with explicit authority and evidence
Trigger A pack becomes invocable through the shared runtime
Successful outcome Only a conformant healthy adapter receives an authorized request
Approving owner
Authorize a bounded work packet and inspect its result
Trigger Work is delegated from an accountable commitment
Successful outcome The owner can distinguish completion, uncertainty and pending review without reading raw logs

User scenarios
Plan and durable background execution
MC-W01 | Baseline scope. An application submits a request needing sustained model or tool work
1. Record objective and input references with the initiating actor
2. Present the proposed plan and required authority
3. Create a durable job before starting its execution
4. Expose progress, journal and artifacts for operator inspection
Edge case A request without a usable provider remains blocked rather than appearing active.
Failure and recovery On cancellation or host loss, preserve the last known state and distinguish acknowledged stop from uncertain execution.
Acceptance Reload the host mid-run and recover the same job identity; no successful state is inferred from a disconnected stream.
Evidence references README.mbt.md#Current Capabilities; docs/PRODUCT_CONTRACT.md#Outcome
Workspace checkpoints and runtime memory
MC-W02 | Baseline scope. A job edits an artifact or needs continuity across sessions
1. Associate one workspace and journal with the run
2. Record relevant artifact revisions and git checkpoints where supported
3. Persist runtime memory with source and producing-run references
4. Let the reviewer open the exact artifact revision
Edge case An uncommitted workspace is still work in progress; a memory entry is not accepted company knowledge.
Failure and recovery A failed checkpoint leaves an explicit incomplete record and preserves available artifacts for inspection.
Acceptance Reopen a completed run and identify the exact inspected revision without promoting its memory into MoonBook.
Evidence references README.mbt.md#Main Subsystems; docs/PRODUCT_CONTRACT.md#Ownership
Gateway and remote agent control
MC-W03 | Baseline scope. An operator selects a configured gateway or ACP remote agent
1. Resolve the versioned session/control protocol
2. Verify transport and scoped authority
3. Start or attach to the intended session
4. Propagate steer, stop and status acknowledgements to the host
Edge case A listed remote capability can be unavailable or unauthenticated.
Failure and recovery After transport loss, show an unknown remote outcome until a status or reconcile response arrives; do not spawn a replacement blindly.
Acceptance A transport fixture covers denial, disconnect and reconnection without presenting an unacknowledged cancellation as final.
Evidence references README.mbt.md#Operator UX; docs/PRODUCT_CONTRACT.md#Capability status
Installed pack capability invocation
MC-W04 | Baseline scope. A planned step names a catalog capability
1. Resolve product/tool@pack-version and its exact schema
2. Recheck active installation, adapter health and authority
3. Send the bounded input and correlation identity to the adapter
4. Attach the adapter receipt and output references to the run
Edge case A catalog entry with expired health is discoverable but not executable.
Failure and recovery Version or schema drift refuses dispatch and explains which contract changed; it does not substitute a similar tool.
Acceptance Exercise healthy, expired, uninstalled and mismatched adapters and verify that only the exact authorized target receives an invocation.
Evidence references docs/CAPABILITY_INVOCATION.md; docs/PRODUCT_CONTRACT.md#Authority and evidence
Unknown outcome reconciliation
MC-W05 | Baseline scope. A process ends or acknowledgement is lost after a potentially effectful invocation
1. Persist the attempt and its last confirmed stage
2. Mark outcome unknown rather than failed
3. Query the adapter using its correlation identity
4. Attach found receipt or confirmed no-effect evidence before offering retry
Edge case A successful receipt still enters result inspection, not automatic acceptance.
Failure and recovery If reconciliation cannot determine the effect, keep retry disabled and expose a manual investigation path.
Acceptance Inject acknowledgement loss after an effect; repeated recovery must resolve to the original effect or remain unknown without duplicate execution.
Evidence references docs/PRODUCT_CONTRACT.md#Authority and evidence; docs/HARNESS_REPLAY.md
Commitment scoped delegated job
MC-W06 | Roadmap scope. MoonProj offers an approved work item for execution
1. Bind commitment, source scope, actor, objective, ceiling and stop condition
2. Validate that the approval covers the selected runtime action
3. Execute under that immutable envelope
4. Return the exact attempt and artifact receipt to the originating task
Edge case A changed objective or budget requires a new approval revision.
Failure and recovery If receipt return fails, retain a pending handoff with the same identity; do not rerun work to repair reporting.
Acceptance One authorized synthetic commitment round-trip preserves every binding and separately records runtime completion and owner review.
Evidence references docs/PRODUCT_CONTRACT.md#Ownership; moon-luna-investigation-ledger-20260930.md
Recovery view for the approving owner
MC-W07 | Roadmap scope. An owner returns after an interruption without runtime expertise
1. Show whether work ran, did not run, remains unknown or awaits review
2. Display the last verified action and available artifact
3. Offer only presently safe reconcile, retry, steer or stop controls
4. Retain advanced journal detail behind the concise summary
Edge case A mixed run can contain completed steps and one unknown effect; summarize both.
Failure and recovery A stale projection must disclose its timestamp and refresh failure rather than offer unsafe controls.
Acceptance Owners correctly identify the safe next action in interruption scenarios; any unknown effect remains visible until reconciled.
Evidence references docs/PRODUCT_CONTRACT.md#Authority and evidence; docs/HARNESS_REPLAY.md

Alternatives and optimality
Direct synchronous tool call
Advantage Minimal integration for one short reversible action
Cost Little durability or interruption recovery
When to choose Prefer it when no background state, review chain or effect reconciliation is needed
Application specific job runner
Advantage Can closely fit one product and existing infrastructure
Cost Duplicates authority, journal and recovery mechanisms across hosts
When to choose Use shared MoonClaw only when common contracts reduce actual integration cost
The runtime boundary concentrates durable execution and recovery while leaving business authority outside. Its value depends on hosts sharing those contracts. Parallel job identities or hidden approval stores would erase that advantage, so the architecture is defensible rather than universally optimal.
Qualify one host, provider route and effectful adapter before expanding the catalog. Demonstrated cancellation and acknowledgement-loss recovery matter more than capability count. Additional remote transports should wait until the existing control contract is stable and its operational cost is understood.
A direct request or established task queue may suit short, reversible work better. MoonClaw should justify adoption through shared controls, inspectable artifacts and safer recovery, measured against that simpler option. A large test suite alone cannot establish superior user value.
The next proof is a commitment-scoped run with an inspected result and an honest interrupted state. Customer acceptance, cash receipt and reviewed learning remain external outcomes. Their absence must not be obscured by calling runtime completion a successful company workflow.
