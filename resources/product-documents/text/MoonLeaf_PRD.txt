MoonLeaf product requirements
OPC OS portfolio  |  30 September 2026  |  Version 1 for product review
MoonLeaf should provide conservative preview and narrowly bounded editing of DOCX, XLSX, PPTX, CSV and TSV through a host such as MoonDesk. Its frozen baseline returns a neutral scene, capabilities and diagnostics, preserves unknown package parts where supported, and verifies a save-as-copy rather than silently rewriting the source. Nine JavaScript document-session tests passed. A synthetic MoonDesk DOCX web preview was checked separately, but full Office fidelity and real-document visual acceptance remain unqualified. The recommended direction is trustworthy business-document intake and a reviewed client copy, not a universal Office replacement.
Repository maturity claim conservative OOXML alpha
This document defines the product baseline and a separately proposed roadmap. Acceptance tests below are release criteria unless a cited observation explicitly says they passed. Current source coverage does not establish production deployment or customer value.
Product philosophy and scope
A preview is a useful representation of a file, not proof that every feature survived or that the user may edit everything visible. MoonLeaf should state what it understands, what it preserves without interpreting and what it cannot safely change. When the requested operation exceeds those capabilities, refusal with a precise diagnostic is preferable to plausible-looking output that loses formulas, layout or package relationships.
The library serves document-host developers. MoonDesk owns file access, user confirmation, destinations and conflict handling; MoonLeaf owns its declared parsing, transformation and evidence contract. In an accountable business workflow, intake produces a source reference, bounded edits produce an inspectable artifact, and MoonProj or another domain owner records delivery and customer acceptance separately. A rendered page is not proof that its claims are true, and a successful save is not evidence of customer approval.

User scenarios
Preview and edit supported DOCX content
MOONLEAF-W01 | Baseline scope. MoonDesk receives a supported DOCX file
1. Validate the archive and package structure
2. Build ordered paragraph and table preview metadata
3. Report capabilities and unsupported layout or content
4. Apply an exact supported text replacement to a copy
5. Reopen and inspect the resulting scene
Edge case Rich layout or a font lies outside the native PDF subset; preview availability must not imply print readiness.
Failure and recovery An unsupported replacement or invalid package fails without changing the source file.
Acceptance Use a supported paragraph and table fixture; replace exact text, reopen the copy and compare order and content. Reject an unsupported layout for print-ready output.

MOONLEAF-W06 | Roadmap scope. An author needs to correct supported content in a customer deliverable

Alternatives and optimality
Native Office application
Advantage Best choice for complex layout formulas animation and established collaboration
Cost Separate application and automation boundary
When to choose Prefer whenever required fidelity exceeds the published MoonLeaf subset
Read only text extraction
Advantage Small implementation surface for indexing simple content
Cost Loses rich visual structure and cannot verify a client copy
When to choose Prefer when the only job is searchable source text with clear extraction limits
External general renderer
Advantage May cover additional formats or typography
Cost Adds operational and fidelity assumptions that require separate qualification
When to choose Do not use as a silent fallback for a failed print-ready gate
The optimal scope is conservative because a business document can be damaged while still looking superficially reasonable. Explicit capabilities and preserved originals are core product value, not temporary disclaimers. Every supported edit should have a narrow transformation contract and a meaningful reopen check.
Library and host maturity need different gates. The nine session tests and separate synthetic Desk preview demonstrate bounded progress, but neither establishes a safe Office replacement. Real-producer documents, malformed archives, host active-content isolation and intended-size visual inspection are the next evidence requirements.
The simpler alternative wins for advanced authoring. Opening the original in a native Office application is better than extending MoonLeaf to an untested corner of charts, formulas or typography just to keep the user inside the suite. MoonLeaf earns its place for reliable intake and small reversible edits that can be described precisely.
The PRD could narrow its first client-copy release to DOCX exact text replacement and CSV or TSV values, while keeping XLSX and PPTX as clearly bounded previews until their copy behavior is qualified. That reduces the simultaneous fidelity surface and lets one complete retained-original to inspected-copy to deliverable-reference journey establish integration value.
